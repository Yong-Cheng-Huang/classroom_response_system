沒有發現整項原始功能被直接刪除。相對原文的限制、釐清及例外均需連同已確認決策閱讀，不能只逐字比對原文便判定違規：

## 4. 審查二：D30 技術架構

**判定：D30 與需求沒有已知根本衝突，可維持；但不能單憑選型保證功能與時限。**

| 選擇 | 可支援的責任 | 必要限制／審查結論 |
|---|---|---|
| TypeScript | 共用輸入型別、驗證契約與錯誤代碼 | 型別不取代執行期驗證；現有 SR01、IA08 與任務 4.5、4.6 已要求伺服器驗證 |
| React | 老師／學生畫面、單題預覽、草稿、結束導向 | 前端不裁定排名或權限；身分交接尚需 R01 補齊 |
| Node.js | HTTP、WebSocket、Google 整合及命令執行器 | 單程序不自動消除 await 間競爭；設計明定有序命令與交易是正確方向，長工作不可阻塞同步 |
| SQLite | 本機持久化、題組交易、組題唯一與排名唯一約束 | 支援交易，並同時只容許一個寫入交易；適合此候選規模，但需短交易及正確處理失敗，不把網路放進交易。[官方交易文件](https://www.sqlite.org/lang_transaction.html) |
| HTTP＋WebSocket | HTTP 命令、WebSocket 角色分流、快照恢復 | HTTP 及重連可能重送；現有 requestId、revision、epoch 與快照銜接設計能處理，仍須落實測試 |
| 單一權威後端 | 接收排序、活動階段、權限與跨分頁一致 | 接收順序定義在命令入口，並非客戶端時間；需補重啟後序號延續，見 R04 |

Node.js 官方文件提醒長時間阻塞事件迴圈會影響其他工作；因此在 42 分頁下，解析、序列化、同步儲存與批次準備不能只以「非同步架構」推定已符合 1 秒要求。[Node.js 事件迴圈文件](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop)

本次沒有負載測試或瀏覽器機制實驗，不宣稱 SQLite／Node.js 已經通過 42 分頁驗收。具體套件與版本可在環境任務鎖定，不需要因本報告改換 D30。

### 6.2 順序及測試判定

大方向為環境→後端→資料→身分→活動→Google→同步→提交→畫面→結果→匯出→整合，合理。早期以固定測試資料或單元替身驗證活動服務並非問題，不因真正匯入尚未完成就判定為循環依賴。

但 tasks 宣告「群組依序執行」，7.7 已要求命令到畫面可量測，9.5 又要求轉入結果，而正式畫面與結果工作仍在後面群組；具體依賴需修正，見 R05。

目前已涵蓋的重要例外包括：同組／跨組競爭、同毫秒、空白不占名次、A→E→B、成功後斷回覆、重啟、過期、舊活動、背景與複製分頁、匯入最後一題失敗、匯出最後一題遺失、人工修改、非系統 I:K、無人作答、已有答案、模式互切、格式還原、公式外觀文字與遠端成功後回覆遺失。缺的是 R01～R04 的精確交錯／恢復狀態，不是完全沒有例外測試。

## 8. 發現的問題與建議修改

以下建議均未套用。位置以本次審查的檔案行號與需求／任務 ID 為準。

### R01［P1／高］分頁身分交接缺少競爭情境的確定規則

**證據：** design L162～L168；IA03（identity-access L30～L41）；任務 4.2、7.4。設計只說「偵測既有持有人」及「搭配導覽類型與伺服器重整交接」，沒有交接狀態、持有人選定及失敗結果。

**可觸發情境：** 原分頁正重新整理、尚未重新持有鎖或建立新連線時，複製分頁同時啟動；或原分頁保有身分但其連線中斷，另一複製分頁先抵達恢復服務。僅以「目前有沒有鎖／連線」不能從文件推導誰可承接原身分。

**影響：** 不同實作可能讓副本承接原身分，或把原分頁誤判成副本而使其喪失正在進行的參與資格。這是設計未定義，不是本次已重現錯誤，也不主張必然無法實現。

**建議：** 不改 D30，先明列分頁建立、續接、重整交接、複製、失去持有權與恢復的狀態及伺服器裁定，說明哪些識別會被複製、哪個證據可承接舊身分。把「原分頁重整＋複製同時發生」「副本先重連」「原分頁關閉後副本恢復」加入 Given／When／Then 與早期驗證任務；若須限制瀏覽器操作語意，必須另取得人工確認，不能默默放寬 IA03。

**關閉條件：** 人工接受一套可執行交接設計與上述驗收情境，任務明確引用；後續實作階段再以實際 Chrome 驗證，不能因還沒有實作就要求本次先寫程式。

技術依據：sessionStorage 在 opener 情境可複製，且支援重新整理與還原；Web Locks 是同來源排他協調，不直接提供「這就是原分頁」的伺服器證明。[sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)、[Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)。

### R02［P1／高］匯出結果不明時阻擋新活動，只在設計出現且沒有退出流程

**證據：** design L182 明定結果不明須「暫停替換」；GE12（guided-notes-export L112～L118）只規定匯出停止與核對；AL03、AL04、GI06 沒有該替換限制或恢復條件；任務 5.5、12.8 未定義永久無法核對時如何處理。

**可觸發情境：** Google 寫入可能完成而回覆遺失，此後原文件刪除或老師失去該文件讀取權；老師準備匯入另一份有效文件。現有 design 要求暫停替換，卻沒有可完成的核對或放棄路徑。

**影響：** 系統可能因舊文件永久不可核對而無限阻擋新活動。這是保護核對資訊的合理動機，但也是新增的外部行為；不能只藏在工程設計，亦不能假設 D31 已授權永久阻擋。

**建議：** 先請人工選定不明匯出的處理政策，再同步 AL／GI／GE 與 design、tasks。候選包括明確的「待核對、已完成、可證未送出、不明」操作狀態及重新授權／再次核對流程；若需要「老師明確確認放棄核對後建立新場次」，其資訊保留範圍與舊文件後續安全性須另行確認，不能本次自行決定。寫入前應持久化恢復核對所需資料，避免僅保存一個不足以判斷內容與排版的狀態標記。

**關閉條件：** 明確定義可觀察阻擋、解除與不可恢復情境，為「遠端寫入不明後永久失去原表權限，再匯入新文件」新增情境與任務，並與 D07、D24 的清除邊界一致。

### R03［P2／中］重啟時「原有效身分」尚未細化為可恢復的連線狀態

**證據：** RR03、RR04；design L98、L166～L168。模型有寬限截止，但啟動流程只概括讀取固定到期及已撤銷狀態，沒有說明一般斷線寬限與伺服器停機的交界如何裁定。

**可觸發情境：** 一位學生在正常服務下已斷線，寬限即將到期或剛到期時程序強制中斷；撤銷可能尚未持久化。重啟不能一律把「沒有撤銷紀錄」視為仍有效，否則可能違反不復活失效身分；也不能一律用重啟時刻扣完整停機時間，否則違反 D04。

**建議：** 定義有效、寬限中、撤銷／到期狀態與持久化邊界，說明正常關機及非正常中斷的恢復判準；對已完成失效交易者絕不復活。新增「斷線後停機」「寬限邊界中斷」「停機期間達 12 小時」的狀態表與情境，必要的不可精確辨識情況列明供人工確認，不自創新的寬限例外。

**關閉條件：** 更新設計與任務 3.2、4.7、7.4、7.5 的完成條件，能對上述時序給出唯一預期結果。

### R04［P2／中］接收順序在重啟後的延續方式未定義

**證據：** SR04、PS01；design L95、L102、L116；任務 2.3、8.4、13.4。已有持久化順序與名次，但未說明命令接收序號計數器如何初始化、恢復與避免重用。

**可觸發情境：** 某題重啟前已有提交，重啟後又接受新提交。若序號從 1 重置或與資料庫配置順序混用，按 receiveOrder 重建／查詢可能將新提交排到舊提交之前；只保存舊 rank 並不自動定義新序號。

**建議：** 明列序號持久化或可比較的世代＋序號策略，以及唯一範圍、啟動恢復、回滾／無效請求可有序號缺口但不占名次等規則。這是設計選擇，無須改 D30 或新增產品功能。

**關閉條件：** 新增「同題已有名次→重啟→新組提交→結果與匯出」情境，驗證順序及新舊名次都不重排；由任務 2.3、8.4 明確承接，而不只寫泛稱重啟測試。

### R05［P2／中］逐群完成順序與畫面／結果依賴不一致

**證據：** tasks L5 宣告群組依序；7.7（L69）要求命令完成到畫面更新可量測，正式畫面在 9、10 群組；9.5（L87）要求結束自動轉結果，結果工作在 11.3（L101）。

**影響：** 執行者可能為勾完前置任務而做暫時畫面、重複完成後續工作，或以後端事件送達代替畫面更新。現有完成條件的可量測性是優點，但依賴圖沒有對齊。

**建議：** 明列任務依賴，將 7.7 拆清楚「後端通道／快照測試」與「畫面端到端時限」；後者置於畫面完成後或既有 13.3。9.5 若只負責路由切換應明說，完整結果呈現由 11.3 完成。不要把各群組單元測試全部移到最後。

**關閉條件：** 任務依賴可由前至後完成，不靠未列入的暫時實作；修改後重算任務總數，不為保留 79 這個數字而合併不相干工作。

### R06［P2／中］效能時限已明確，但驗收負載與量測程序不足以重現

**證據：** RR02、RR05、RR07；design 測試策略；任務 7.7、13.2、13.3。已確定 42 分頁、1 秒、5 秒，但未固定測試題目量、操作批次、重複次數、背景／暫停狀態與具體「畫面更新」量測點。

**影響：** 六題範本輕載或只記錄事件到達即可宣稱通過，另一環境以大量題組及真實 DOM 完成時間卻得不同結果。「本機正常運作」也不足以區分支援中的背景分頁與作業系統暫停情形。

**建議：** 補可重現的驗收配置與程序：記錄機器、macOS、Chrome；固定單題／題組資料集及同時提交／重整批次；定義伺服器完成、DOM 套用、服務恢復可用的觀測點；記錄每次結果與重複次數，確認使用最壞值而非只報平均。背景分頁與瀏覽器凍結如何分類若改變承諾，必須人工確認；不得自行排除已要求的背景分頁或放寬 1／5 秒。

**關閉條件：** 不必現在證明效能已達成，但應在實作前能照同一程序驗收；測試資料規模不是新增產品題數上限。
